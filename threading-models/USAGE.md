# Использование программы

Все команды ниже выполняются из каталога проекта:

```sh
cd threading-models
make help
make build
```

Нужен Go 1.25 или новее. Программа использует только стандартную библиотеку.
Из корня LaTeX-репозитория можно вызывать `make -C threading-models ...`.

## Один запуск

```sh
make run
make run SCENARIO=logs MODE=mn WORKERS=8 PROCS=4 TASKS=1000 RECORDS=256
make run SCENARIO=compress MODE=pinned WORKERS=16 PROCS=4
```

Каждая команда запускает один опыт. В stdout выводится одна JSON-строка после проверки результата.
В stderr попадают сообщения об ошибках, код завершения неуспешного запуска — ненулевой.
`make run` не печатает команды сборки в stdout, поэтому результат можно перенаправить в файл:

```sh
mkdir -p results
make run SCENARIO=logs MODE=mn > results/logs-mn.jsonl
```

Перенаправление `>` заменяет содержимое выбранного файла; `>>` добавляет запись.

## Режимы исполнения

| Режим | Команда | Организация обработки |
|---|---|---|
| `seq` | `make run-seq` | Последовательный обход задач |
| `mn` | `make run-mn` | Фиксированный пул обычных горутин |
| `pinned` | `make run-pinned` | Такой же пул с закреплением горутин за потоками ОС |

Параметры нагрузки доступны и в этих целях: `make run-pinned SCENARIO=compress PROCS=4`.
`pinned` сохраняет планировщик Go и служит приближением 1:1. Привязка к ядрам не устанавливается.
В `seq` параметры WORKERS и QUEUE сохраняются в конфигурации, но пул и очередь не используются.

## Задачи и параметры

`logs` разбирает записи формата `service,status,latency_us,bytes` и собирает статистику.
Общее число записей равно `TASKS × RECORDS`. Сейчас агрегация локальная с итоговым объединением.

`compress` сжимает независимые блоки DEFLATE. Лёгкие и тяжёлые задачи используют один алгоритм,
но разные размеры блоков. Увеличение блока или уровня сжатия изменяет полезную работу и её стоимость.

| Переменная Make | Флаг программы | По умолчанию | Назначение |
|---|---|---|---|
| `SCENARIO` | `-scenario` | `logs` | `logs` или `compress` |
| `MODE` | `-mode` | `mn` | Режим для цели `run` |
| `WORKERS` | `-workers` | `4` | Число горутин обработки |
| `PROCS` | `-procs` | Доступные логические CPU | GOMAXPROCS |
| `QUEUE` | `-queue` | `16` | Ёмкость очереди; 0 — без буфера |
| `TASKS` | `-tasks` | `100` | Число задач |
| `RECORDS` | `-records` | `256` | Записей в одной задаче `logs` |
| `BLOCK_BYTES` | `-block-bytes` | `16384` | Размер лёгкого блока `compress` |
| `HEAVY_BLOCK_BYTES` | `-heavy-block-bytes` | `262144` | Размер тяжёлого блока |
| `HEAVY_PERCENT` | `-heavy-percent` | `10` | Процент тяжёлых задач по количеству |
| `LEVEL` | `-level` | `-1` | DEFLATE: -1 — стандартный, -2 — Huffman, 0–9 — уровни |
| `DATA_SEED` | `-data-seed` | `42` | Начальное состояние генерации данных |
| `ORDER_SEED` | `-order-seed` | `2026` | Начальное состояние перемешивания задач |
| `WAIT` | `-wait` | `0s` | Ожидание таймера после полезной обработки |
| `REPEATS` | — | `3` | Повторов каждого режима в `compare` |
| `RESULTS_DIR` | — | `results` | Каталог результатов `compare` |

Примеры:

```sh
# Только лёгкие блоки, без ожидания.
make run SCENARIO=compress HEAVY_PERCENT=0
# Смесь 90/10 по количеству, блоки 16 КиБ и 1 МиБ.
make run SCENARIO=compress BLOCK_BYTES=16384 HEAVY_BLOCK_BYTES=1048576 HEAVY_PERCENT=10
# Управляемое ожидание; это модель ожидания, не измерение реального I/O.
make run SCENARIO=logs WAIT=1ms WORKERS=32 PROCS=4
```

При `logs` параметры блоков и уровня сжатия не меняют полезную обработку; при `compress` RECORDS не используется.
Доля тяжёлых задач округляется вниз до целого количества. Фактическое количество находится в `heavy_tasks`.
Изменение смеси меняет общий объём данных: при сравнении разных смесей учитывайте `summary.input_bytes`.

## Сравнение трёх режимов

```sh
make compare SCENARIO=compress WORKERS=8 PROCS=4 REPEATS=10
```

Будет выполнено 30 независимых запусков: по 10 на режим с вращением порядка режимов.
Каждый запуск `compare` создаёт новый файл JSONL в RESULTS_DIR и печатает его путь.
Каждая строка файла — отдельное измерение. При ошибке серия останавливается, уже записанные строки сохраняются.
MODE для этой цели не используется: она всегда запускает все три режима.

Для пары режимов сохраняйте одинаковые данные, размеры, состав, seed и параметры исполнения.
`workload_sha256` должен совпадать. Изменение ORDER_SEED меняет выдачу задач, но сохраняет состав.
Прогрев, температурная стабилизация и анализ повторений не автоматизированы; порядок режимов их не заменяет.

## Чтение результата

- `status: "ok"` и `verified: true` — результат прошёл проверку.
- `duration_ns` / `duration_ms` — время обработки с выдачей задач и объединением.
- `bytes_per_second` — входные байты в секунду; `summary.stats.records` — число записей журналов.
- `summary.tasks_completed`, `input_bytes`, `compressed_bytes` — фактически обработанный объём.
- `config`, `generator`, `workload_sha256` — условия воспроизведения нагрузки.
- `go_version`, `os`, `arch`, `logical_cpus` — сведения об исполняющей среде.

Генерация, создание горутин, закрепление, проверка и вывод находятся вне измеряемого интервала.
Рабочие выделения памяти внутри Run и WAIT входят в него. Память и число потоков ОС пока не измеряются.
Для форматирования одной записи можно использовать `python3 -m json.tool < results/logs-mn.jsonl`.

## Проверки и сборка для Ubuntu

```sh
make check        # vet, тесты и проверка гонок; для -race требуется поддерживаемый C toolchain
make fmt          # форматирование Go-файлов
make build-linux  # bin/experiment-linux-amd64, без cgo
make cli-help     # все флаги; бинарный файл можно запускать и без Make
```

Бинарный файл Linux amd64 предназначен для Ubuntu на Intel. Проверки под `-race` не являются замерами скорости.
