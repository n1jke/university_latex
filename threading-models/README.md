# Сравнение моделей многопоточности

MVP курсового проекта по архитектуре вычислительных систем. Только Go stdlib, Go 1.25+.
Два типа задач: разбор журналов (`logs`) и сжатие блоков DEFLATE (`compress`).
Каждый тип — структура со своим конструктором, конфигурацией и `Run(context.Context)`.

Команды Make, параметры, серии запусков и поля результатов описаны в [USAGE.md](USAGE.md).

## Быстрый запуск

```sh
make build
./bin/experiment -scenario logs -mode mn -workers 4 -procs 4
./bin/experiment -scenario compress -mode pinned -workers 16 -procs 4
./bin/experiment -help
```

Один процесс выполняет один опыт и выводит одну JSON-строку в stdout; ошибки — в stderr.
Пример сравнения одинаковой нагрузки (каждый режим — отдельный процесс):

```sh
mkdir -p results
for mode in seq mn pinned; do
  ./bin/experiment -scenario compress -mode "$mode" \
    -workers 8 -procs 4 -tasks 100 -queue 16 \
    -block-bytes 16384 -heavy-block-bytes 262144 -heavy-percent 10 \
    -data-seed 42 -order-seed 2026 >> results/compress.jsonl
done
```

`seq` — последовательный эталон. `mn` — фиксированный пул обычных горутин.
`pinned` — такой же пул с `runtime.LockOSThread` на каждой горутине обработки.
Это приближение отображения 1:1 внутри Go runtime: планировщик и ограничение GOMAXPROCS сохраняются.
Закрепление не означает привязку к ядру. Программа пока не измеряет число живых потоков ОС.

## Параметры

- `-tasks`: количество единиц работы; `-records`: записей в одной LogsTask.
- `-block-bytes`, `-heavy-block-bytes`: размеры двух классов CompressTask.
- `-heavy-percent`: доля тяжёлых задач по количеству; округление вниз отражается в `heavy_tasks`.
- `-level`: уровень DEFLATE; `-wait 1ms`: дополнительное моделируемое ожидание после задачи.
- `-workers`, `-procs`, `-queue`: горутины, GOMAXPROCS и ёмкость очереди (0 — без буфера).
- `-data-seed`, `-order-seed`: содержимое данных и порядок выдачи задач.

Описание сценария находится в `internal/config.Default`; CLI переопределяет параметры.
YAML, общая агрегация под мьютексом, удержание общего ресурса, трейсы и метрики оставлены развитию.
Сейчас статистика локальная с итоговым объединением. При `logs` настройки сжатия не меняют нагрузку.
При `compress` параметр records не используется. `wait` означает таймер, а не реальный I/O.

Вход сжатия — повторяющиеся сообщения с детерминированным шумом. Это модель данных для эксперимента.
Чистая серия: `-heavy-percent 0`; смесь: например 90/10 по числу задач.
При изменении состава и размеров меняется общий объём байтов: для сравнения смесей подберите `-tasks`
и проверяйте `summary.input_bytes`. Между режимами весь конфиг нагрузки должен совпадать.

## Модули и решения

`config` → `scenario` → `task` / `tasks` → `executor` → `experiment` → `output`.
`cmd/experiment` связывает CLI с экспериментом. Тип задачи не выбирает режим и не создаёт пул.
Сценарий строит список и независимый эталон статистики; исполнитель сохраняет результаты по позиции,
даже если они завершились в другом порядке. Каждый экземпляр задачи используется один раз.

Выбран общий интерфейс задачи, чтобы смена режима не меняла полезный алгоритм. Отдельные реализации
алгоритмов для каждого режима отклонены: они смешивали бы влияние планирования и полезной работы.
Вместо внешних сервисов MVP использует локальную подготовку и структурированные логи.

| Требование | Реализация | Проверка |
|---|---|---|
| Одинаковая работа во всех режимах | Общие Task и Scenario | Сравнение fingerprint и полезного результата |
| Корректная обработка | Генератор-эталон и восстановление DEFLATE | Проверка каждой задачи после таймера |
| Воспроизводимая смесь | Два seed, фиксированное число классов | Проверка состава и изменения порядка |
| Завершение при ошибке | Контекст, отмена и ожидание горутин | Ошибка задачи и отмена при занятой очереди |

Контекст проекта: родительский каталог `../`, документы RFC-001 и RFC-002.
Старого формата конфигурации и миграций в новом проекте нет.

## Что измеряется

Таймер стартует после генерации данных, конструкторов и готовности горутин (включая закрепление).
Включены выдача через очередь, полезная обработка, ожидания задач и объединение результатов.
После остановки снимаются закрепления, проверяется результат и пишется JSON.
Входы только читаются, рабочие буферы сжатия выделяются внутри Run и входят в измерение.
Сжатые блоки сохраняются до проверки; память включает все эти результаты.

Статистика проверяется по ожидаемым значениям, рассчитанным генератором независимо от парсера.
Для сжатия каждый блок восстанавливается и сравнивается с исходным; проверка вне таймера.
`workload_sha256` включает порядок, идентификаторы, размеры и содержимое задач.
PCG, формат генерации и оба seed записываются в лог; настройки алгоритма находятся в `config`.
Успешная запись содержит `verified: true`, `status: ok`; неуспех возвращает ненулевой код.

MVP не выполняет прогрев и серию повторов автоматически: запускайте независимые процессы,
чередуйте режимы и сохраняйте все записи. Перед итоговым исследованием зафиксируйте версии ОС/ядра,
RAM, режим питания, параметры сборки и состояние стенда; лог содержит Go, GOOS, GOARCH и число CPU.
Измерения под `-race` нужны для проверки гонок, а не для сравнения производительности.
Генерация ограничена бюджетом 512 МиБ входа, но это не лимит общей памяти процесса.

## Проверки

```sh
make check
```

Проверяются одинаковые полезные результаты во всех режимах, смеси и seed, ошибки конфигурации,
отмена при заполненной очереди и завершение соседних горутин при ошибке задачи.
Без внешних зависимостей, Docker и сервисов наблюдения.
