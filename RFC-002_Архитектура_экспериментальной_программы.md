# RFC-002: Архитектура программы и содержание раздела 4

Статус: **предложение для обсуждения**. Дата: 27.10.2026.
Основание: [RFC-001](Исследование_для_разделов_3–5.md), раздел 3 и уточнения по реализации.
Здесь описаны целевая архитектура и этапы её реализации; текст отчёта подготавливается после обсуждения.

## 1. Цель и границы

Разработать модульную программу на Go для запуска параметризуемых задач в режимах `seq`, `mn`, `pinned`.
Одна реализация полезной работы используется во всех режимах. Модель исполнения выбирается независимо
от типа задачи. Добавление нагрузки не должно требовать изменения алгоритма выдачи задач.
В MVP реализуется общий механизм и два простых типа задач; сложные нагрузки добавляются итерациями.

## 2. Модули и ответственность

| Модуль | Ответственность |
|---|---|
| `cmd/experiment` | Выбор сценария, запуск и код завершения |
| `internal/config` | Типизированное описание запуска и проверка параметров |
| `internal/scenario` | Подготовка данных, списка задач, смеси и эталонного результата |
| `internal/task` | Контракт задачи и результата |
| `internal/tasks/logs` | Разбор записей и частичная статистика |
| `internal/tasks/compress` | Сжатие независимого блока |
| `internal/executor` | Последовательный запуск и пул горутин в двух режимах |
| `internal/experiment` | Подготовка, границы измерения, объединение, проверка и завершение |
| `internal/output` | Логи запуска и результатов; последующее подключение диагностики |

Это рекомендуемое разбиение по ответственности. В MVP близкие компоненты могут быть небольшими файлами
одного пакета; отдельные сервисы и динамические плагины не требуются.

## 3. Задача как структура с конструктором и Run

Задача — одна единица полезной работы, например разбор пакета записей или сжатие блока.
Сценарий — подготовленный набор таких задач с данными и ожидаемым результатом.
Исполнитель определяет, где запускается `Run`; сама задача не создаёт пул и не меняет GOMAXPROCS.

```go
type Task interface {
    Run(ctx context.Context) (Result, error)
}

func NewLogsTask(cfg LogsConfig, input []byte) (*LogsTask, error)
func NewCompressTask(cfg CompressConfig, input []byte) (*CompressTask, error)
```

Каждый конструктор проверяет конфигурацию и сохраняет её вместе с входными данными в структуре.
`Run` использует сохранённые параметры. Идентификатор и класс задачи хранятся в элементе сценария.
`Result` содержит идентификатор типа, обработанный объём и соответствующие типу выходные данные.
Для MVP допустим явный набор вариантов результата: статистика журналов либо сжатый блок.
Время измеряет модуль эксперимента, поэтому задача возвращает полезный результат без собственного логирования.

Один экземпляр задачи запускается один раз. Для повторения сценарий создаёт новые экземпляры и состояние.
Входные данные доступны только для чтения; изменяемые буферы принадлежат отдельному запуску задачи.
Конструкторы и генерация данных выполняются до старта измерения; рабочие выделения внутри Run учитываются.
Отмена проверяется между блоками работы; она не означает мгновенного прерывания библиотечного вызова.

## 4. Параметры и первые типы задач

Общие параметры запуска: режим, GOMAXPROCS, число горутин, ёмкость очереди, объём данных и оба seed.
Параметры нагрузки: размер блока, число записей, уровень сжатия, доля классов, ожидание и синхронизация.
Проверяются диапазоны, совместимость параметров и обработка последнего неполного блока без потери данных.

**Первый тип — LogsTask:** разбирает небольшой пакет записей и возвращает частичную статистику.
Настройки: формат записи, количество записей в пакете и фильтр; это относительно лёгкий кандидат.
**Второй тип — CompressTask:** сжимает блок тех же подготовленных данных с заданным уровнем.
Настройки: размер блока и уровень сжатия; это кандидат для более длительной полезной работы.
Относительная стоимость подтверждается пилотом: название типа не гарантирует конкретное время.

Желаемая длительность CPU-задачи задаётся объёмом реальной работы, а не выполнением до истечения таймера.
При одинаковом объёме сравниваются режимы; цикл «работать N секунд» изменил бы объём на разных системах.
Для ожидания предусматривается `wait_duration`, для модели критической секции — `hold_duration`.
Это отдельные параметры: ожидание таймера без мьютекса и удержание общего мьютекса дают разную нагрузку.
Задержка — заданная нижняя цель ожидания, фактическое время зависит от планирования и измеряется отдельно.
Сон под мьютексом допустим только как явно обозначенная модель, а не имитация CPU-вычислений.
Общую агрегацию и моделируемый общий ресурс следует подключать явно через состояние сценария.

## 5. Лёгкие/тяжёлые задачи и одинаковая нагрузка

Нагрузка описывает тип, конфигурацию, количество экземпляров и класс задачи: лёгкая или тяжёлая.
Для исследования размера сначала смешиваются конфигурации одного типа, например два размера блока сжатия.
Смесь LogsTask и CompressTask — отдельный опыт: там одновременно меняются объём и характер работы.
Доли 90/10 задаются по числу задач; объём данных и доля байтов отражаются дополнительно.
`data_seed` задаёт данные, `order_seed` перемешивает заранее сформированный список с точными долями.
Для пары режимов совпадают список, порядок выдачи и данные; расписание выполнения остаётся свободным.
Чистые серии каждого типа предшествуют смешанным, чтобы можно было объяснить результат смеси.

## 6. Исполнение и измерение

Цикл: конфигурация → подготовка → готовность горутин → старт → Run → объединение → стоп → проверка → лог.
Подготовка и проверка вне интервала; выдача задач, полезная работа и объединение входят во время обработки.
В `mn` и `pinned` одинаковые W горутин и очередь; закрепление выполняется до сигнала готовности.
При завершении используется UnlockOSThread. В `seq` те же задачи выполняются последовательно.
Ошибки отменяют запуск, горутины завершаются; частичные результаты не считаются успешным измерением.
Сжатие проверяется восстановлением исходного блока вне интервала; статистика — по последовательному эталону.
MVP пишет один итоговый структурированный лог с параметрами, длительностью, объёмом и статусом проверки.
Подробные логи отдельных задач по умолчанию выключены: их запись влияет на очередь и время обработки.

## 7. Итерации — рабочие заметки, не содержание отчёта

**Сейчас, MVP:** сценарии и параметры задаются структурами в Go; два типа задач; три режима исполнения;
проверка результата и итоговые логи времени. Используется общий путь проверки конфигурации и создания задач.
Текущий этап — проектирование: эти возможности ещё не следует описывать как уже реализованные.
**Следующая итерация:** YAML преобразуется в те же структуры, тип выбирается через фабрику задач;
добавляются новые нагрузки и варианты общей статистики, ожидания и конкуренции за ресурс.
**Диагностика:** метрики, трассировки и дашборды Grafana; pprof и анализ flame graph отдельными прогонами.
Grafana визуализирует данные через выбранное хранилище/источник; способ доставки определяется отдельно.
Расширения подключаются к управлению экспериментом, не меняя алгоритмы задач; базовый режим без них сохраняется.

## 9. Предлагаемые решения для согласования

Принять LogsTask и CompressTask для MVP, интерфейс Run с context и результатом, конфигурацию в конструкторах.
Принять раздельные параметры вычислительной работы, ожидания и удержания общего ресурса.
YAML и диагностические подключения развивать поверх общей модели конфигурации после работающего ядра.
